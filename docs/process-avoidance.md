> 修订方式：走 issue 讨论 + 评论留痕（AGENTS.md 规则 4/9/10），不进本文件存量改。

## 0. 适用场景（按需取用，勿全文套用）

| 场景 | 适用条目 |
|---|---|
| UI/行为实跑轮次与复盘 issue | A1 / A2 / A3 / C1 / C2 |
| 写测试、复核消费宿主契约面的代码 | B1 / B2 |
| 涉及 dsh 插件面改动（loader/bundle patch、client 注入、sessions 契约消费等） | B3（规则 11 执行抓手） |

## 1. 破坏性分类（三层）

| 层 | 定义 | 典型后果 |
|---|---|---|
| L1 流程机制 | 拆分/验收/闭环方式的设计缺陷 | 单点修复、相邻同面漏网、假闭环 |
| L2 验证基建 | 测试与门禁不能反映真实语义 | 缺陷一测必现却测不出来、覆盖率达标但语义空转 |
| L3 认知契约 | 对宿主/框架契约的理解偏差且无执行抓手 | 用错 API（如 subagentAddress 当反查用）、官方参考不读 |

## 2. 规避措施分类（预防 / 检测 / 闭环）

### A. 预防（开 issue / 定方案时）

- **A1 强制回归轮**：每轮新实跑前，先对上一轮**所有已合并 PR** 做现场 UI/行为逐字段对照清单
  （格式以事故报告「宣称验收 vs 实际残留」对照表为母版），逐项打勾后才开新轮。
  落点与时序：回归清单在开 issue 前完成的 → 进正文；开 issue 后完成的 → 进首条评论并在正文
  标注「回归结果见评论」（与规则 9「正文一经创建不可修改」协调）。
- **A2 同面扩散验收（验收边界 ≠ 变更边界）**：验收项必须覆盖本修复区块的**所有相邻字段/入口**
  ——修「最近协作事件」摘要必须同时列出并验收「当前活动」；修跳转必须列「未打开过的会话」场景。
  **相邻字段验收发现缺陷时，显式二选一并记入验收清单结论**：(a) 同 PR 修复，或 (b) 当场拆
  新 issue 跟踪、本 issue CLOSE 不受影响；严禁静默打勾通过。相邻同面是验收边界不是变更边界：
  不得以「扩大变更半径」为由跳过相邻验收，也不得以「并入本 PR」为由无度膨胀半径（规则 1）。
- **A3 两段式完成定义（合并门槛 ≠ 闭环门槛）**：
  - **合并门槛 = CI 全绿**（机器可判，沿用 AGENTS.md 规则 2）；
  - **CLOSE 门槛 = 现场现象消失 + 带证据的复测评论**（复测两档见 A4）。
  不允许「现象未复测即 CLOSE」；PR 合并后必须补一条复测确认评论才允许 CLOSE issue。
- **A4 现场复测两档（A3/C1 共用证据标准）**：
  - 开发侧「隔离宿主验证」：独立 profile 双隔离实跑 + 截图/录像证据（合并后可立即做）；
  - 「用户现场实跑」：CLOSE 前最终确认。
  子 agent 无现场环境时走隔离档并附证据；CLOSE 的最终确认升级给维护者/用户（衔接角色界定），
  不无限自等。

### B. 检测（写测试 / 复核代码时）

- **B1 契约同构 mock 纪律**：凡消费宿主契约面的代码，测试 mock 必须按宿主真实实现语义构造
  （写 mock 前读宿主源码），mock 上方注释「对照 dsh-repo <仓库相对路径>:<方法/语义>」——行号
  仅为 8-30 快照，验证时以当前源码为准（防行号腐化）；评审抽查「对照注释在场且指向存在文件」。
- **B2 正向用例补盲 + 字段级语义断言**：
  - 每个降级/回退分支除「兜底不抛错」外，必须补「主路径成功后被调用目标正确」的正向断言
    （例：refreshSubagents 成功后应 open(childId)/openSubagent(childId)）；
  - 验收断言一律展开到**字段级语义**（具体内容/取值来源，如 summary 文本、title、
    rounds/maxRounds 取值），「可见/可用/能打开」字眼必须展开为具体字段断言。
- **B3 官方参考对照（AGENTS.md 规则 11 执行抓手）**：涉及 dsh 插件面/契约消费面改动时，
  issue 方案评审与 PR review 环节强制检查「对照官方哪个文件:行号」留痕，无留痕即评审不通过
  （与规则 11 的口径衔接：类型包 + 源码示例双层对照）。

### C. 闭环（合并后 / 复盘时）

- **C1 滚动清单核销**：复盘类 issue 保留「已闭环/未闭环」逐项清单（`- [x]`），合并 PR 时逐项
  核销并附 A4 复测证据；未复测的项不移除。
- **C2 两级触发，禁止等第三次**：
  - **第二次出现**即触发「同族合并评估」：在 issue 评论显式给出「合并评估 / 单点拆分」裁决；
    正文/评论中已存在的「建议合并评估」信号必须显式处理，不得静默忽略；
  - **第三次出现（同族信号被忽略过）**：禁止再单点拆分——先写根因事故报告 + 按本表分类定
    规避措施，再拆修复（事故报告路径记入 issue 关联）。

## 3. 根因 ↔ 措施映射（覆盖完备性核对）

| 事故根因（INC-2026-08-30 报告 §4/§2） | 对应条目 |
|---|---|
| 验收口径只覆盖「改了的边」不覆盖「相邻同面」 | A2 |
| 测试 mock 与宿主真实语义不同构 | B1 / B2 |
| 跨 issue 依赖的展示层片段无端到端联合复测 | A1（回归上一轮）+ A2（当轮字段级语义） |
| 三轮回溯无强制回归轮 | A1 |
| 「合并即闭环」替代「现象闭环」 | A3 / C1 |
| 官方参考不读（L3） | B3 |

## 4. 执行检查表（评审与（半）自动检查共用最小机检面）

- [ ] 回归轮：本 issue/PR 是否引用「上一轮已合并 PR 的现场对照清单」（正文或首条评论）？
- [ ] 同面扩散：相邻字段/入口是否逐项验收？发现缺陷是否显式「同 PR 修 / 拆新 issue」二选一？
- [ ] 字段级语义：验收断言是否展开到具体字段（summary/title/rounds/maxRounds），非「可见」裸词？
- [ ] 现象闭环：CLOSE 前是否有人（隔离档或用户档）复测「用户可感知的现象消失」？（评论留痕）
- [ ] 契约 mock：消费宿主契约面的 mock 是否按真实语义构造并注释对照位置（可 lint 模式检查）？
- [ ] 正向断言：每个降级分支是否补了「主路径成功时调用目标正确」断言？
- [ ] 官方对照：dsh 插件面改动是否在 issue/PR 留痕官方文件:行号？（评审阻断项）
- [ ] 滚动清单：复盘 issue 的「已闭环/未闭环」清单是否逐项核销、未复测项未移除（可脚本解析）？
